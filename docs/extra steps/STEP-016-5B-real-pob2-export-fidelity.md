# STEP-016.5B — Real PoB2 export fidelity validation

**Date:** 2026-09-27  
**Status:** PLANNED  
**Roadmap reference:** Phase 4 / STEP-016.5B  
**Authoring context:** Cursor-assisted development

## 1. Objective

Close the final fidelity gap in the PoB2 importer by validating it against **real export codes generated by the current Path of Building 2 application**.

STEP-016.5 and STEP-016.5A already established the raw PoB2 importer, safe decode/decompression/XML parsing, passive-tree compatibility, skill-group preservation, display-list-aware `mainActiveSkill` handling, and conservative support-role resolution.

The remaining gap is that fidelity fixtures are still synthetic XML encoded to look like PoB2 exports.

STEP-016.5B must prove that the importer behaves correctly with export strings actually produced by PoB2 itself.

Do not implement the PoB2 calculation engine. Do not implement character-aware scoring.

---

## 2. Why this step exists

Current validation is:

```text
our interpretation of PoB2 save format
        ↓
synthetic XML
        ↓
our importer
```

We also need:

```text
real PoB2 application
        ↓
real Export action
        ↓
real encoded build string
        ↓
our production importer
```

This can expose real save-time details such as omitted/default attributes, element ordering, root/version attributes, `mainSocketGroup`, `mainActiveSkill`, `SkillSet`/`ItemSet` defaults, weapon-set serialization, and format changes.

---

## 3. Acceptance criteria

- [ ] At least four real PoB2-generated export codes are added as fidelity fixtures.
- [ ] The exact PoB2 version or commit used is recorded.
- [ ] Fixtures come directly from PoB2 export output, not handwritten XML.
- [ ] No private player/account data is required.
- [ ] Fixture A validates one active skill with true supports.
- [ ] Fixture B validates multiple skill groups and main socket-group selection.
- [ ] Fixture C validates a non-trivial `mainActiveSkill` / display-skill-list case.
- [ ] Fixture D validates weapon-set or other non-trivial tree serialization.
- [ ] The visible PoB2 interpretation is manually recorded for each fixture.
- [ ] Automated tests assert the importer matches that recorded interpretation.
- [ ] Real exports pass the full production decode/import path.
- [ ] Synthetic error/security fixtures remain in place.
- [ ] Existing passive-tree analysis remains unchanged.
- [ ] Existing 016.5A skill-role rules remain unchanged unless real-export evidence proves a bug.
- [ ] Required repository checks pass.
- [ ] Create `docs/progress/STEP-016-5B-real-pob2-export-fidelity.md`.

---

## 4. Scope

STEP-016.5B may add real PoB2 fixtures, provenance metadata, fidelity tests, and minimal parser corrections proven necessary by real exports.

It must not add PoB2 calculations, character-aware scoring, gear ranking, pobb.in fetching, GGG changes, poe.ninja changes, or AI interpretation.

---

## 5. Fixture creation procedure

For each mandatory fixture:

```text
1. Open the current Path of Building 2 application.
2. Create a small local test build.
3. Configure the exact scenario needed.
4. Record what PoB2 visibly shows.
5. Use PoB2's own Export action.
6. Copy the resulting export code.
7. Store that exact export code as the test fixture.
```

Do not recreate the XML manually and do not compress handwritten XML for these fidelity fixtures.

---

## 6. Version pinning

Record the exact PoB2 version used to create the real fixtures.

Prefer:

```text
version: 0.23.1
commit: <commit if known>
```

If a newer release is current when this step runs, use that current release and document it.

All real-fixture expectations must be tied to the recorded PoB2 version.

---

## 7. Fixture privacy

Fixtures must be locally-created test builds with no private account data.

Avoid unnecessary account names, personal notes, private league metadata, or copied community builds.

Document fixture provenance explicitly.

---

## 8. Fixture A — Simple active + supports

Create a real PoB2 build with:

```text
one main skill group
one active skill
at least two genuine support gems
```

Record from PoB2:

```text
main socket group
main active skill
support names
enabled/disabled state
```

Expected importer behavior:

```text
main skill resolved
correct active skill
correct supports
no non-support active gem misclassified as support
```

---

## 9. Fixture B — Multiple skill groups

Create a real PoB2 build with at least two skill groups and explicitly select the second or later group as the main socket group.

Record all groups, which group is main, main skill, supports, and other active groups.

Expected importer behavior:

```text
all groups preserved
correct group selected
other groups retained
support relationships remain group-local
```

---

## 10. Fixture C — Non-trivial display-skill list

This fixture is mandatory.

Use a build where:

```text
displaySkillList != raw gem list
```

For example, use a gem that contributes multiple active/display effects.

Record:

```text
display entry 1
display entry 2
...
selected main active skill
source gem/effect where deterministically knowable
```

Expected importer behavior:

```text
mainActiveSkill is interpreted as a display-list index
not a raw gem index
```

If the importer cannot reconstruct the display list safely, it must leave the main skill unresolved and mark the import partial rather than guess.

---

## 11. Fixture D — Weapon-set/tree serialization

Create a real PoB2 build with:

```text
shared passive allocations
plus weapon-set/specialisation allocations
```

Record:

```text
shared ids
set1 ids
set2 ids
set3 ids if present
```

Expected importer behavior:

```text
shared ids stay shared
weapon-set ids stay separate
no accidental merging
all ids validated against active GGG pin
```

---

## 12. Optional Fixture E — Equipment serialization

If easy, add a real export with an equipped item containing a useful mix of implicit/explicit and crafted/fractured/enchant text.

Use it to validate actual item-text parsing.

This is recommended but not mandatory if the four required fixtures provide sufficient coverage.

---

## 13. Truth records

For each fixture, store a small human-readable truth record separate from the importer implementation.

Example:

```text
fixture: fireball-supports
PoB2 version: 0.23.1

PoB2 UI:
main socket group: 1
main active skill: Fireball
supports:
- Magnified Area II
- Lightning Attunement

expected importer:
mainSkill.resolved: true
mainSkill.name: Fireball
supportNames:
- Magnified Area II
- Lightning Attunement
```

Expected results must be based on PoB2 itself, not on current importer output.

---

## 14. Fixture storage

Use a dedicated fixture directory, for example:

```text
packages/data-sources/src/pob2/fixtures/real/
```

Each fixture should contain the real export code and its truth/provenance metadata.

Avoid placing very long export strings directly inside test source files when a fixture file is clearer.

---

## 15. Full production-path testing

Every real fixture must pass through the same entry point used for user-pasted imports:

```text
raw export code
→ decodePob2Export
→ zlib inflate
→ XML parse
→ provider model
→ normalization
→ tree compatibility
```

Do not pre-decode the fixture and bypass Base64, decompression, size limit, or XML parsing.

---

## 16. Root and format validation

Record the actual root element and relevant format/version attributes emitted by current PoB2.

Lock the real observed root into regression tests.

If both `PathOfBuilding2` and `PathOfBuilding` remain accepted, document which one current PoB2 emits and why the other remains supported.

---

## 17. Skill-shape validation

Compare actual exported:

```text
Skills
SkillSet
Skill
Gem
mainSocketGroup
mainActiveSkill
mainActiveSkillCalcs
```

against importer assumptions.

If actual exports omit fields that synthetic fixtures always supplied, update the importer conservatively.

Do not invent defaults unless PoB2 behavior clearly establishes them.

---

## 18. Main-skill and support fidelity

For the real fixtures, assert:

```text
selected main group
selected main active/display skill
support classification
unknown-role count
```

Fixture C must specifically prove that `mainActiveSkill` is not treated as a raw gem index.

---

## 19. Weapon-set fidelity

For Fixture D, assert the real export's shared/set1/set2/set3 allocations map exactly as PoB2 serialized them.

Do not infer membership from connectivity.

---

## 20. Tree compatibility

Run all real fixtures against the existing active GGG passive-tree pin.

Record each fixture as:

```text
compatible
partial
incompatible
```

Do not edit real fixture passive ids just to make tests pass.

Version-string mismatch may warn; unknown passive ids remain the stronger incompatibility signal.

---

## 21. Parser corrections discovered by real fixtures

If a real export exposes a bug:

1. add a failing regression test;
2. document the actual observed export shape;
3. make the smallest deterministic correction;
4. preserve ambiguity rather than guessing;
5. update normalization version only if normalized semantics materially change.

Do not silently patch behavior.

---

## 22. Normalization version

Current PoB2 normalization version after STEP-016.5A is:

```text
2
```

Do not increment it merely because real fixtures were added.

Increment only if real-export evidence forces a semantic normalization change.

Document any bump.

---

## 23. Source checksum

Do not change checksum semantics.

The checksum continues to identify the decoded/inflated source payload.

Real-fixture tests should verify:

```text
same export
→ same checksum
```

Normalization version remains separate from source identity.

---

## 24. Keep synthetic fixtures

Do not remove synthetic fixtures for:

```text
invalid Base64
invalid zlib
oversized decompression
invalid XML
DOCTYPE/ENTITY rejection
unknown passive ids
malformed mainActiveSkill
targeted edge cases
```

Real fixtures prove fidelity. Synthetic fixtures prove controlled error handling. Both are required.

---

## 25. Security regression

Preserve all STEP-016.5 security rules:

```text
raw-code-only import
no remote fetch
1 MiB inflated limit
DOCTYPE rejection
ENTITY rejection
server-side parsing
no raw XML rendered as HTML
```

No new network dependency is required.

## 26. Browser verification

Paste at least one real PoB2 export into the actual analysis screen and verify:

```text
import succeeds
summary renders

passive-tree heuristic warning remains visible
```

Do not add new product features here.

## 27. Passive-analysis regression

Real PoB2 imports must continue to use the existing passive-analysis engine.

Do not create PoB-specific ranking behavior.

For a real fixture that matches a known tree allocation, compare candidate paths and score against the equivalent existing fixture where practical.

---

## 28. Character-aware scoring remains out of scope

Even after real-export validation, imported skills, supports, items, and configuration must not alter:

```text
heuristicScore
offensive profile
defensive profile
balanced profile
Top-K ranking
semantic completeness
```

The UI/docs must continue to say that current optimization is passive-tree heuristic only.

---

## 29. Do not broadly expand the skill fact table

Do not hand-copy large portions of PoB2's gem database during this step.

If a real fixture requires a missing fact, add only the minimum checked fact needed and document its source/version.

A broad skill-data ingestion strategy belongs in a separate future step.

---

## 30. Required automated tests

Add tests covering at minimum:

- real Fixture A decodes through the production importer;
- Fixture A main skill matches PoB2;
- Fixture A supports match PoB2;
- Fixture B selects the correct main group;
- Fixture B preserves non-main groups;
- Fixture C does not equate `mainActiveSkill` with raw gem index;
- Fixture C matches PoB2's display-skill selection or remains explicitly unresolved;
- Fixture D preserves weapon-set allocations;
- real fixture checksums are stable;
- real fixture normalization is deterministic;
- tree compatibility is deterministic;
- synthetic security tests still pass;
- fixture/GGG flows still pass;
- passive scoring regressions still pass.
